# Elden Ring player resources, equip load and rune cost

Max HP, FP, stamina and equip load, how gear changes attributes and resources, the equip-load
tiers, and what a level costs. The implementation is `scripts/er-mechanics-resources.py`
(`--selftest` passes 50 checks; `--corpus` gives the agreement table in section 8).

Labels:
- **VERIFIED**: read from regulation params (installed 1.17.1 `regulation.bin`, through
  `scripts/er-param-read.py`) or from the executable.
- **INFERRED**: consistent with the data, but the code path was not traced.
- **SITE**: the er-build-planner JS bundle (`~/.cache/er-build-planner/js/notifications-BSZ1DATO.js`,
  offsets 3496000 for the tables, 3652000-3678000 for the character class).
- **COMMUNITY**: not needed.

Every EXE address is a 1.16.2 VA from the named Ghidra dump on :8765 (dump VA = deobf VA = live VA
on 1.16.2). All of these functions sit below the `0xafefe9` boundary. In the installed 1.17.1
image each one moved by `+0xe50`, found by a masked byte search with `scripts/find-deobf-bytes.py`
over `eldenring-deobf-1.17.1.bin`: `0x140687570`->`0x1406883c0`, `0x140687640`->`0x140688490`,
`0x1406876d0`->`0x140688520`, `0x14068d000`->`0x14068de50`, `0x140686370`->`0x1406871c0`,
`0x14068c630`->`0x14068d480`. Each hit still carries the same graph id in its `mov edx,imm32`, and
the three weight-tier floats read the same values. So the formulas below hold for the installed
build (VERIFIED).

## 1. The curve: `PerformCalcCorrection`

Every resource is one `CalcCorrectGraph` row evaluated at an effective attribute.
`PerformCalcCorrection(float x, uint graphId)` @ `0x140690f30` works like this (VERIFIED, from the
decompile and from the disassembly of the clamp block at `0x1406910ce`..`0x140691175`):

```
row = CalcCorrectGraph[graphId]                      GetCalcCorrectGraphParam 0x140d34270
x   = min(x, stageMaxVal4)
if not x > 0: return stageMaxGrowVal0
i   = first stage with x <= stageMaxVal[i+1]         (i in 0..3)
t   = (x - stageMaxVal[i]) / (stageMaxVal[i+1] - stageMaxVal[i])
e   = adjPt_maxGrowVal[i]
c   = t**e                 if e >= 0
    = 1 - (1 - t)**(-e)    if e <  0
v   = grow[i] + c * (grow[i+1] - grow[i])
return clamp(v, min(grow[i], grow[i+1]), max(grow[i], grow[i+1]))
```

All of it runs in single precision (`float`, `mulss`/`addss`, `powf`). The planner uses the same
shape in double precision (SITE `getCorrectionGraphValueAt`).

## 3. Rates: how gear multiplies resources

VERIFIED: `CS::SpecialEffect::GetMaxHpRate` @ `0x1404fbe60`, `GetFPRate` @ `0x1404fbf00`,
`GetMaxStaminaRate` @ `0x1404fbf90` and `CalculateEquipWeightChangeRate` @ `0x1404f8080` all use
the same loop:

```
rate = 1.0f
for each SpEffect entry on the character (skipping entries with flags & 0x800c0003):
    r = field of its SpEffectParam row
    if r > 0: rate *= r                                  float product; 0 or negative is ignored
return rate * GetMPLevelCorrection(graph 300/301/302)     (not applied to equip load)
```

The fields are `maxHpRate` (+0x10), `maxMpRate` (+0x14), `maxStaminaRate` (+0x18) and
`equipWeightChangeRate` (+0xe4). The offsets were read from the `movss` operands and match the
Smithbox paramdef (VERIFIED). So **every source multiplies**. Nothing is added. Erdtree's Favor +2
with Crimson Amber +2 gives `1.04 * 1.08`, not `1.12`. `GetMPLevelCorrection` @ `0x1404f60a0`
returns 1.0 unless SpEffect 590 or 592 (0x24e/0x250) is active. Those are the multiplayer
level-sync effects, so solo play is x1.0 (VERIFIED). The HP and stamina per-entry getters
(`0x1404ffc70`, `0x1404ffe00`) also multiply by `ClearCountCorrectParam.MaxHpRate`/`MaxStaminaRate`
when a flag field is set. That is NG+ scaling for enemies, and no talisman or armor row sets it
(INFERRED from the row data).

**Truncation matters.** 60 Vigor with Erdtree's Favor +2: `1900 * 1.04f = 1975.99993`. That
rounds to the float `1975.99988` and `cvttss2si` gives **1975**. The planner computes in double,
stores `pv(x) = +x.toFixed(8)` = 1976 and displays 1976. 218 corpus builds hit this kind of
off-by-one on HP and 17 on FP (section 8). The game-side value follows from the instructions; it
was not observed on screen.

## 4. Attributes added by gear

VERIFIED: `CS::SpecialEffect::CollectStatBuffs` @ `0x1404f3fd0` sums nine signed bytes over the
same entry list: `addLifeForceStatus` (Vigor, +0x31e), `addWillpowerStatus` (Mind),
`addEndureStatus` (Endurance), `addVitalityStatus` (an unused fifth slot), `addStrengthStatus`,
`addDexterityStatus`, `addMagicStatus` (Int), `addFaithStatus` and `addLuckStatus` (Arcane,
+0x326). `CalculateStatus` then sets `effective = min(base + sum, 99)` for each attribute. There is
no lower clamp. The resources in section 2 are evaluated at the effective value, so +5 Endurance
from Radagon's Soreseal raises stamina and equip load. The status calculator's effective stats
come from this code. That the live character's `PlayerGameData+0x288..` effective fields, read by
the `Perform*CalcCorrection` callers, hold the same value is INFERRED (same inputs, same fields).

## 5. Equip-load tiers

VERIFIED: `CalculatePlayerWeight` @ `0x14068bda0` gives `ratio = burden / maxLoad` (a float
division, 0 when maxLoad <= 0). `GetWeightType` @ `0x14068c630` then compares it with three
`.rdata` floats: 1.0 @ `0x14329e678`, 0.7 @ `0x143b33d50` and 0.3 @ `0x143b33d54` (1.17.1:
`0x1432a1938`, `0x143b37d60`, `0x143b37d64`, same values). **All comparisons are strict**
(`comiss` + `ja`/`jbe`):

| ratio | type | roll |
|---|---|---|
| <= 0.3 | 1 light | light roll (INFERRED) |
| (0.3, 0.7] | 2 medium | medium roll (INFERRED) |
| (0.7, 1.0] | 3 heavy | fat roll (INFERRED) |
| > 1.0 | 4 overloaded | cannot roll (INFERRED) |

Type 0 ("super light") is returned only when SpEffect stateInfo 115 is active, and stateInfo 102
forces type 4. No SpEffect row in 1.17.1 uses either stateInfo (VERIFIED scan), so for players
only 1..4 occur. NPC Tarnished take their ratio from `PlayerCommonParam.npcPlayerAnalogWeightRate_*`
(0/26/51/101 %) through `NpcParam.npcPlayerWeightType` instead. The planner uses `<30 Light, <70
Medium, <100 Heavy` (SITE), so exactly 30.0% and 70.0% land one tier higher there than in the game,
and exactly 100% is "Overloaded" on the site but heavy in game. Which roll animation each type
plays lives in the behavior scripts and was not traced.

**Burden** (VERIFIED `CS::PlayerIns::CalculateEquipmentWeight` @ `0x140247b80`) is the float sum of:
- `EquipParamWeapon.weight` (+0x10) over the six hand slots (loop `cmp edi,6`). Arrows and bolts
  are not in the sum.
- `EquipParamProtector.weight` (+0x24) over five armor slots.
- `EquipParamAccessory.weight` (+0xc) over five talisman slots.

Only four armor and four talisman slots exist in the UI, so the fifth of each is presumably empty
(INFERRED). Great-rune goods have no weight. Max load is `maxLoad` from section 2. It is not
rounded, and the in-game display precision was not checked.

## 6. Rune level and cost

**RL identity.** Every `CharaInitParam` class row 3000..3011 satisfies
`soulLv = sum(baseVit..baseLuc) - 79`, e.g. Vagabond `88-79=9`, Wretch `80-79=1`, Heavy Knight
`89-79=10` (VERIFIED, `--selftest` checks all 12). Each level buys exactly one attribute point, so
`RL = sum of the eight base attributes - 79` for any character. That is INFERRED: the level is a
separate `PlayerGameData.level` field, and no code was found deriving it. The planner uses the same
identity (SITE `getStatTotalForClass`, `reduce(..., -79)`). The maximum is `8*99 - 79 = 713`.

**Cost.** `SoloParamRepositoryImp::CalculateLevelUpCost(level)` @ `0x140686370` reads
`CalcCorrectGraph` row 200 (`init_inclination_soul` 0.1, `adjustment_value` 1,
`boundry_inclination_soul` 0.02, `boundry_value` 92; the `movss` offsets are +0x3c/+0x40/+0x44/+0x48):

```
x    = float(level + 80)
cost = trunc( powf(x, 2) * (0.02f * max(0, x - 92) + 0.1f) + 1 )      all float, cvttss2si
```

`level` is the level being bought: the stat screen shows `CalculateLevelUpCost(this->level + 1)`
(`FUN_1407c83a0`, menu field 0x271a), and the multi-level cost list `FUN_140970d30` sums
`CalculateLevelUpCost(n)` for `n = from+1 .. to` (VERIFIED). So going from L to L+1 costs
`cost(L+1)`, with `x = L + 81`. Samples: level 2 costs 673, level 10 costs 811, level 100 costs
60,265, level 151 costs 153,680 and level 713 costs 8,879,349. Levels 1..713 total 1,692,566,879
runes.

The float arithmetic makes the cost 1 rune lower than a double-precision evaluation at 126 of 712
levels. The first ones are 25, 30, 32, 60 and 115. The planner and the usual wiki formula compute
in double.

**The planner's "to next level" is one level off** (SITE bug). `calculateSoulsToLevelUp(e = rl + 1)`
evaluates `(e+81)`, i.e. the cost of level rl+2. The game shows the cost of level rl+1. At RL 150
the planner shows 156,090 and the game 153,680. The planner's total from class level to RL sums the
right levels, but in double precision.

## 7. Stamina per attack (param level only)

VERIFIED: `CS::PlayerGameData::GetConsumeStaminaRate` @ `0x140684430`, called from
`CS::PlayerIns::GetConsumeStaminaRate` @ `0x140651e90`, which truncates the result:

```
consumed = trunc( base
                * SpecialEffect::GetConsumeStaminaRate(se)                          0x1404f7470: product of per-entry rates != 1
                * (EquipParamWeapon.staminaConsumptionRate if flags & 3 else 1)
                * (PlayerCommonParam.lowStatus_ConsumeStaminaRate = 1.5 if the weapon's
                   requirements are not met, per HasStatsForWeapon, else 1) )
```

`base` arrives as an argument from a virtual call site, which was not traced. It is most likely
`BehaviorParam_PC.stamina` of the attack behavior (INFERRED from the field name and the values).
Weapon rows are `100000000 + behaviorVariationId*1000 + judgeId`. Longsword
(`behaviorVariationId` 200) has stamina 12 on judges 0..40, 20/30 on 100/105 and 110/115, and 15 on
120. What `EquipParamWeapon.attackBaseStamina` (Longsword 45) feeds was not found.

## 8. Agreement with the planner corpus

`--corpus` runs the model over `~/.cache/er-build-planner/builds.jsonl` (5699 builds). It uses the
stored `stats`, the equipped talismans and armor (`equipIndex != null`, which is the active set)
and `greatRune`, and compares with `build.computed`. Buckets:
- `exact`: the game model equals the planner.
- `rounding`: the planner's own double arithmetic on the same inputs reproduces its number, so the
  difference is only float32 vs float64 at a truncation.
- `skipped`: the build has an item name the module cannot resolve, or rl 0.
- `other`: anything else.

| quantity | n | exact | rounding | skipped | other |
|---|---|---|---|---|---|
| rl = sum - 79 | 5604 | 5366 (95.75%) | 0 | 38 | 200 |
| max HP (floor) | 5135 | 4857 (94.59%) | 218 | 7 | 53 |
| max FP | 5129 | 5080 (99.04%) | 17 | 0 | 32 |
| max stamina (floor) | 5128 | 5060 (98.67%) | 0 | 3 | 65 |
| max equip load (+-0.001) | 5128 | 5100 (99.45%) | 0 | 0 | 28 |
| runes.total | 4791 | 30 | 4761 | 0 | 0 |
| runes.toNextLevel vs game (level rl+1) | 4791 | 0 | 0 | 0 | 4791 |
| runes.toNextLevel vs level rl+2 | 4791 | 4491 | 300 | 0 | 0 |

Model plus rounding explains 99.0% (HP), 99.4% (FP), 98.7% (stamina) and 99.5% (load) of the
builds, and every rune number. The rest:

- **rl = sum - 79, 200 builds.** The stored rl is inconsistent with the stored stats. 122 have rl
  above the sum, 46 below, 27 have no class, and 5 match once attributes are clamped to the class
  base. This is planner data, not game rule.
- **Resource "other", 110 distinct builds.** The planner's value is always higher, by ratios that
  cluster on known effects not present in the exported equipment: HP x1.25 (21, Morgott), x1.15
  (11), x1.10 (6); stamina x1.20 (29), x1.15 (15); equip load x4.5 (11). Many of these builds name
  a different great rune or none. Probable cause: effects the planner applies from state that is
  not in the export (`character.activeEffects`, custom effects), or a stale `computed` block.
  Neither can be checked from the file.
- **Unresolved names** (Smithbox row names predate 1.17): Steel Helm/Armor/Gauntlets/Greaves, Gold
  Tattoo (Arm/Leg), Gauntlets, Broken Gold Mask, Leontiel's set, Silver Grooved set, and Ancestral
  Spirit's Horn. None of them is in the armor/talisman effect tables above except where noted, so
  they are unlikely to change resources, but they are skipped rather than assumed.
- **Duplicate talisman slots**: 13 cases equip the same talisman twice (Great-Jar's Arsenal x8).
  The module reports these as `accessoryGroup conflict`.

## Not established

- How the exported talisman or armor SpEffect gets onto the character's entry list (resident vs
  `refId`). The model applies `refId` (refCategory 2) plus all resident ids, which reproduces the
  corpus.
- That the live `PlayerGameData` effective attributes equal `min(base + CollectStatBuffs, 99)`.
  This was traced in the status calculator only.
- Where `accessoryGroup` exclusivity is enforced.
- The goods -> SpEffect link for great runes (600 + 10k), and whether Rune Arc alone (SpEffect 490
  and 499 carry `maxHpRate` 1.3) changes HP in play.
- Roll animation per weight type, and how the equip-load and HP floats are displayed in game.
- The caller that passes the base stamina into `GetConsumeStaminaRate`, and the role of
